Memba: how the codebase is holding up

The short version

The inside is built better than the front door

This is a healthy, unusually disciplined codebase. The findings cluster into two themes, and neither is about the code you write most often.
  • The care is unevenly distributed. Aggregates, the release process, and token handling are built like they'll run for decades. The HTTP boundary and production operability are still at prototype standard: both Postmark webhooks are unauthenticated, nothing rate-limits, and production has no health check, error tracker, or metrics sink.
  • Long-horizon event-sourcing habits aren't established yet. No event versioning strategy, no business timestamps on events, and one table that's half projection, half operational state. These cost nothing today and compound with every event written.

Overall maintainability: strong. The work ahead is mostly closing the gap between the weakest parts and the very high standard the rest of the code already sets — ideally before real clubs and imported history arrive.

Calibration

What's genuinely working

  • solidThe ADRs are true. Every implementation claim I spot-checked matched the code. The read-model-changes pattern (ADR 21) is in all 11 projectors without exception.
  • solidDeploys verify the database. Release.verify_repo_schema! compares the live schema against the app's expectations and fails the deploy on drift. Very few teams do this.
  • solidToken and session security. 32-byte random tokens, hashed at rest, 15-minute TTLs, single-use with row locking, session renewal on login/logout, enumeration-resistant sign-in.
  • solidBoundaries hold. The web layer basically never touches Repo directly; Messaging reaches Membership only through its public API.
  • solidThe shared feature files are real. ~97 of 122 Cucumber scenarios genuinely run at both the domain and browser layers, with tag discipline that's documented and self-tested.
  • solidZero sleeps in the test suite — strong-consistency projectors designed the flakiness out. Zero TODO/FIXME markers in lib/. Compile is clean under warnings-as-errors.
  • solidEmail dispatch can't double-send, even multi-node: claims are atomic conditional updates at the database.

Fix first

Both Postmark webhooks accept anonymous POSTs

majorThe inbound endpoint is the serious one. POST /webhooks/postmark/inbound has no signature, secret, or IP check, and the sender is identified purely from the From header of the payload.

What that means in practice: anyone who finds the URL can post a message into a club as any member whose email they know — and Memba will email it to the whole club. The status webhook (/webhooks/postmark) is also open, so delivery records and auth-email progress can be forged too.

  • This was flagged in the kaizen log on 2026-06-02 and in ADR 16's own consequences; it's still open.
  • The Resend endpoints do verify signatures — properly (HMAC, constant-time compare, replay window). But they silently skip verification when the secret isn't configured. Prod is saved by a boot-time raise; the fail-open branch is still a footgun.
  • Fix: shared secret in the Postmark webhook URL plus Postmark's published IP ranges, and make Resend fail closed in prod. The Resend signature module is the template — this is days, not weeks.

Fix first

Nothing in the app rate-limits anything

majorNo Hammer, no PlugAttack, no throttle of any kind — confirmed by exhaustive search.

  • The expensive case: POST /get-started and the sign-in link request both send a real provider email to any address, unauthenticated and unbounded. That's email-bombing of arbitrary inboxes on your Postmark bill, and a reputation risk with the provider.
  • The quieter cases: token callback endpoints (sign-in, invitations, email verification) have no attempt throttling. Tokens are 256-bit so brute force isn't realistic, but there's no defense-in-depth. The webhooks have no flood cap either.
  • Related token hygiene while you're in there: invitation and stop-follow links never expire (invitations grant club membership — an old inbox leak is a real exposure), and spent sign-in tokens are never swept.

A plug-based limiter on the four or five public endpoints that send email or consume tokens covers most of this in an afternoon.

Production operability

Right now, you'd find out prod is broken from a user

majorOr from the Fastmail smoke test, if you happen to run it. There's no other signal.

  • No health check. fly.toml has no checks block, so Fly routes traffic to a booted-but-broken app (projector crashed, DB unreachable) indefinitely.
  • No error tracking. No Sentry/AppSignal/Honeybadger. A crashing projector or dispatcher shows up only as unstructured lines in fly logs.
  • Telemetry defines metrics but ships them nowhere. The reporter line is commented out; LiveDashboard is dev-only.
  • moderatePHX_HOST silently defaults to example.com in prod — broken sign-in links rather than a failed boot. It should raise like DATABASE_URL does.
  • moderateProduction database SSL is a commented-out line for the repo and both event stores. Probably fine on Fly's private network — but make it a documented decision, not an accident.

Production operability

The email dispatcher has three sharp edges

The core design is good — claim-based, idempotent, provider failures rescued and recorded. The edges are around it:

  • moderateNo recovery sweep. Dispatch only fires when a projection-change nudge arrives. Deliveries left pending across a deploy or crash sit there until an unrelated send happens to trigger a sweep.
  • moderatedispatching is a black hole. A crash between claiming a delivery and calling the provider strands the row where neither the nudge path nor manual retry (which only targets failed) can ever touch it.
  • majorA projection rebuild would re-send email. Rebuilding the email-delivery projection recreates history as pending; the next nudge hands all of it to the provider. The code-health ledger flagged this in June (iteration 038); there's still no replay guard, and the replay-safety test stops the dispatcher first — so the dangerous configuration is exactly the one not tested.

The third item is a symptom of a deeper modeling question — next slide.

Event-sourcing durability

Three things to settle before the event store grows

  • majorNo event versioning strategy. Zero upcasters. Schema evolution so far lives as shims scattered through domain code: no-op applies for a dead event, dual string/atom-key matching in Person, a legacy 1970 timestamp constant baked into an aggregate. Each one is an upcaster written in the wrong place, and every aggregate and projector must forever know every historical shape. Adopt upcasters and write the ADR before the next event-shape change.
  • majorEvents have no business timestamps. Projectors stamp rows at projection time, so rebuilds produce different data than the original run — which defeats the point of being able to rebuild. It's already user-visible: "member since" is projection-commit time, and the planned club-history imports bring real join dates this can't represent. metadata.created_at is sitting right there unused.
  • majorThe email-delivery table is half projection, half operational state. A projector inserts rows; the dispatcher then mutates them through its lifecycle. Dispatch outcomes are unrecoverable state in a rebuildable table, and rebuilding re-sends email. Either emit dispatch-outcome events or move dispatch state to its own table — an ADR-level decision either way.

Event-sourcing durability

Smaller domain-model debts, worth a line each

  • moderateMessage and ConversationFollowers share one event stream (same aggregate ID). It works via mutual no-op applies, but Message has no catch-all apply — a future event type on that stream crashes rehydration of old messages. Undocumented; needs an ADR and a one-line guard.
  • moderateTwo EventStore modules, one physical schema. The ADR 7 context split isn't reflected in storage; only typed-ID prefixes prevent stream collisions. Split it or document the sharing.
  • moderateThe event-sourced-vs-plain-Ecto boundary is sensible but unwritten. Accounts, onboarding requests, and the verification-token table (which lives inside the event-sourced Membership context) are exactly where the next contributor guesses wrong. ADR 2 says exceptions must be explicit; they aren't yet.
  • moderateUniqueness checks race. Club slug, duplicate membership, and email ownership are check-then-dispatch against projections — two concurrent requests can both pass, and the failure mode is permanent (two clubs, one slug).
  • moderateMulti-step flows have no compensation. Invitation acceptance and onboarding conversion dispatch 2–3 commands in sequence; a mid-sequence failure strands partial state and retries then dead-end. Same shape in the inbound-accept flow, where a failed rejection email is silently never sent.

Web layer

Multi-tenancy: safe today, but by convention

auditedFirst the good news: I audited every member-facing surface for cross-club access by ID manipulation, and there is no hole. Every view checks both club membership and record ownership.

  • major riskBut the guarantee is per-view discipline, not structure. The centralized on_mount hook that would enforce membership at the live-session level exists in IdentityAuth — and has zero callers. Each LiveView independently remembers to call a loader that forbids. The next live route added with a naive mount ships with no membership check on WebSocket mounts, and nothing will fail.
  • Wire :require_active_club_member into the :club_member live_session and keep the per-record loader checks as defense-in-depth — that's what their own moduledoc says they're for.
  • moderateMySettingsLive checks only that a club exists, not that you belong to it. Nothing leaks (the data shown is self-scoped), but it breaks the pattern everyone else follows.

Web layer

Member pages: live updates are wired inconsistently

  • moderateThe dashboard refreshes on the wrong signal. It re-queries the entire club home when any delivery projection changes in any club — but doesn't subscribe to message changes at all, so a new conversation never appears live. The delivery-details page — whose whole point is live status — has no subscription and tells the member to "check again in a moment." The message page does it right; align the other two, and move to per-club topics before real load.
  • moderateMember surfaces hold full collections in socket memory (all members, all conversations, name maps) while the admin area consistently uses streams. With imported club history coming, port the streams pattern over.
  • moderate~200 lines of copy-paste across the four member LiveViews (session/club helpers, identity derivation, five different initials/1 implementations). One shared scope hook + helper module deletes it.
  • moderateLeftovers: the dashboard and message LiveViews render templates stranded in controllers/page_html/ (which the controller never uses), and the receipt-group code that iteration 047 obsoleted is still in MemberMessageLive.Show, dead.

Code organization

The context modules are getting heavy

  • moderatemembership.ex is 1,823 lines / 46 public functions; messaging.ex is 1,469, of which about a thousand are the inbound-email pipeline. Both are still internally tidy, but the extractions are obvious: an InboundEmailPipeline module and the email-verification token machinery.
  • moderateDomain code reaches into the web layer for URL building — MembaWeb.Endpoint and ClubSite aliased from the stop-follow token, welcome email, and dispatcher. Invert it with a URL-builder the domain owns.
  • moderateSide-effect boundaries are inconsistent: outbound mail goes through the dispatcher (good), but rejection email is sent synchronously inside a command path, and invitation emails are sent from two LiveViews. Every new surface has to remember to email.
  • moderateStill open from the ledger: the reply boundary doesn't verify the conversation ID points at a root message — one small guard away.
  • niggleA batch of small duplications: normalize_email ×4, the projector list in two places, list_member_email_deliverys (sic) in a public API.

Test architecture

Tests: strong shape, rising bill

The dual-layer Cucumber setup is one of the most faithfully executed I've seen, and the coverage shape is genuinely good. The costs to watch:

  • major costThe suite is mostly serial with heavy per-test churn. Every event-sourced test stops all 11 projectors, truncates the event store and projections, and restarts everything — ~150 tests' worth. It's the honest price of a shared Postgres event store, but it's the dominant and growing cost. On top of that, every mix test invocation drops and rebuilds the database, even single-file runs.
  • moderate~14,000 lines of step-definition glue for 122 scenarios, including one 3,951-line JS support file, plus a hand-rolled domain Cucumber runner on top of an unpinned GitHub fork.
  • moderateThe source-scanning guardrail tests have grown to four files (~540 lines) asserting literal CSS strings — and the hardcoded member-page list has already drifted: every member surface added since iteration 047 is missing from the no-hex checks.
  • moderateIsolation by convention: the Fake provider is a global singleton reset by convention; one careless async: true test breaks it silently.

Closing

Five decisions worth making on purpose

Cheap to decide, expensive to inherit by accident:

  • Single node or cluster? Commanded is configured node-local (two nodes would double-run every projector) while DNSCluster is wired as if clustering is coming. Write the "single-node for now" ADR or make it cluster-safe.
  • Should every member see per-recipient delivery status and bounce reasons? They currently can. If that's the product intent, document it — it's a privacy posture, not an implementation detail.
  • Are the invitation-profile and get-started controller flows exceptions to ADR 15, or migration debt? Either answer is fine; the ledger has carried the question for a month.
  • PII in immutable events. Names, emails, and full message bodies live forever in the event store. A membership product will eventually need an erasure story (crypto-shredding or equivalent) — better chosen early.
  • Delivery-details expansion state: URL-addressable per ADR 23, or documented as a transient exception. Decide once, close the thread.
