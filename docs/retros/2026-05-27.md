# 2026-05-27 Fabro/devenv sandbox debugging retro

## What we achieved

- Added Git to the Fabro devenv container image in a way Fabro can find on the default container `PATH`:
  - `pkgs.git` is linked into `/bin` via `containers."fabro-dev".layers[].copyToRoot`.
  - Verified inside the rebuilt image that `command -v git` returns `/bin/git` and `git --version` works.
- Added writable Fabro workspace roots to the image:
  - `/repos`
  - `/workspace`
  - Because the image runs as UID/GID 1000 (`user:user`), these paths are created through a Nix derivation and made writable using the layer `perms` option.
- Added CA certificate environment variables required for HTTPS Git clone before the devenv shell startup has run:
  - `SSL_CERT_FILE = "${pkgs.cacert}/etc/ssl/certs/ca-bundle.crt"`
  - `NIX_SSL_CERT_FILE = "${pkgs.cacert}/etc/ssl/certs/ca-bundle.crt"`
- Changed the image working directory from `/workspace/memba` to `/workspace`.
  - This prevents the image build from baking in a root-owned `/workspace/memba` directory that blocks Fabro from creating `/workspace/memba -> /repos/mattwynne/memba`.
- Rebuilt and loaded the image on the Fabro host via the `hub.local` project.
- Verified manually on the Fabro host that the current image can:
  - create `/repos/mattwynne` and `/workspace` as the runtime user;
  - clone `https://github.com/mattwynne/memba` into `/repos/mattwynne/memba`;
  - create `/workspace/memba` as a symlink to the checkout;
  - run `git rev-parse --is-inside-work-tree` from `/workspace/memba`.
- Documented the current knowledge in `docs/reference/fabro-devenv.md`.
- Committed and pushed the image changes:
  - `727e6b4 Make Fabro sandbox workspace writable`
  - `74999b9 Complete Fabro Docker sandbox image requirements`

## What we learned

From cloning and reading `fabro-sh/fabro`, especially:

- `lib/crates/fabro-sandbox/src/docker.rs`
- `lib/crates/fabro-sandbox/src/clone_source.rs`

Fabro Docker sandbox internals are currently:

- `WORKING_DIRECTORY = "/workspace"`
- `REPOS_ROOT = "/repos"`
- the run container starts with `/bin/bash -lc 'mkdir -p /workspace && sleep infinity'`
- for GitHub origins, Fabro runs a clone/link command shaped like:

```sh
mkdir -p /workspace /repos/<owner> && \
  git -c maintenance.auto=0 -c gc.auto=0 clone \
    --branch <branch> --single-branch --depth 10 --no-tags -- \
    <clone-url> /repos/<owner>/<repo> && \
  ln -s /repos/<owner>/<repo> /workspace/<repo>
```

So a custom Docker image for Fabro needs, at minimum:

- `/bin/bash`
- `git` on the default execution `PATH`
- CA certificates usable by Git over HTTPS
- a runtime user that can create/write `/workspace` and `/repos`
- no pre-existing non-writable `/workspace/<repo>` path

We also learned two devenv container specifics:

- Adding `git` to top-level `packages` is not enough for Fabro's pre-shell clone step. It may exist in the devenv profile after startup, but Fabro needs `git` during sandbox initialization.
- `containers.<name>.copyToRoot` is not the right place for root-level files like `/bin/git`. Devenv treats top-level `copyToRoot` as project/home content and copies it under `/env`. For root-level paths, use `containers.<name>.layers[].copyToRoot`.
- Nix store paths are read-only. If a layer copies a derivation to `/repos` or `/workspace`, `chmod` in the derivation alone is not enough. Use the layer `perms` option to set mode/owner in the image layer.

## What still puzzles us

The current manual test succeeds, but Fabro sandbox initialization still fails.

Known facts:

- The image tag on the Fabro host has the latest config:
  - working dir `/workspace`
  - `SSL_CERT_FILE` set
  - writable `/repos` and `/workspace`
- Manual clone from inside `ghcr.io/mattwynne/memba-fabro-dev:latest` succeeds on the Fabro host.
- Fabro run events show it is using `ghcr.io/mattwynne/memba-fabro-dev:latest` and sees branch `main` / SHA `74999b9...`.
- Fabro logs still report only:

```text
Failed to clone repo into Docker sandbox: Cloning into '/repos/mattwynne/memba'...
```

Possible explanations to investigate next:

1. Fabro is resolving or pulling a different image than the one being tested manually, despite the tag appearing the same.
2. The Fabro server's Docker daemon / image cache differs from the Docker daemon used in our manual SSH tests.
3. The clone URL used by Fabro includes a GitHub App token whose authentication or permission path is failing, but the error is being redacted down to only the first line.
4. The run container environment during Fabro init differs from the manual `docker run` environment in a way not visible from the high-level logs.
5. Fabro deletes the failed container immediately, making post-mortem inspection hard even with `--preserve-sandbox` because initialization fails before preservation helps.

## Suggested next debugging steps

- Find a way to preserve or inspect the failed Docker run container before deletion. If Fabro always deletes on initialization failure, consider temporarily testing with a local patched Fabro or server log level that captures full clone stderr.
- Compare Docker image IDs from:
  - manual `docker image inspect ghcr.io/mattwynne/memba-fabro-dev:latest`
  - Fabro server-side Docker daemon if different
  - any image pull performed by Fabro during sandbox initialization
- Run Fabro with more verbose/debug logging if possible and inspect full worker logs.
- Test a workflow with `[run.clone] enabled = false` plus a prepare step that runs the exact clone command, so the container survives long enough to inspect environment differences.
- Consider using a unique immutable image tag instead of `latest` to rule out image-cache ambiguity.
