# GOOS: acceptance-test-driven development

**Reading reference — Steve Freeman & Nat Pryce, _Growing Object-Oriented Software, Guided by Tests_ (Addison-Wesley, 2009).** Primary-source excerpts, official figures and author commentary—not a full-book reading. Below, **Evidence** paraphrases inspected sources; **Apply** is this reference’s interpretation.

## Practical reading notes

- **Outside in, with two feedback loops.** **Evidence:** the official diagram starts with a failing acceptance test, then cycles through failing unit test → passing implementation → refactoring before returning to the acceptance cycle [1]. **Apply:** express the next externally meaningful outcome first; use small unit-test cycles to discover its implementation, not a large untested implementation sprint. Reading pointer: ch. 5, “Start Each Feature with an Acceptance Test,” p. 39 [4].
- **Start with a walking skeleton.** **Evidence:** the contents place “First, Test a Walking Skeleton” at ch. 4, p. 32; the worked example starts at ch. 10, p. 83 [4]. Pryce says system tests should exercise packaging, deployment and startup, and writing them first exposes integration concerns early [2]. **Apply:** begin with a minimal real end-to-end path that can be built, deployed and tested; extend it incrementally. This operational recommendation synthesizes those sources; the walking-skeleton chapter’s prose was not accessible and its frequently repeated definition is deliberately not quoted.
- **Acceptance is a purpose, not necessarily a UI-wide scope.** **Evidence:** Pryce distinguishes customer-facing acceptance tests of domain logic from unit tests of individual objects, values or small clusters, and from system tests through published interfaces/UI [2]. **Apply:** retain end-to-end evidence for wiring and deployability, but do not force every domain rule through the UI. Unit success alone does not demonstrate the assembled feature.
- **Boundaries support fast feedback.** **Evidence:** Pryce explicitly relates GOOS to Ports and Adapters: domain-facing ports isolate technical infrastructure; acceptance tests can exercise the isolated domain through those ports. Integration tests check owned abstractions against third-party implementations [2]. **Apply:** choose a test boundary deliberately; fast domain acceptance tests complement, not replace, real integration/system tests.
- **Maintainability comes from listening to tests.** **Evidence:** the publisher’s ch. 2 excerpt describes using unit tests and mock collaborators to discover supporting interfaces [5]. Pryce argues that difficult tests should prompt design changes; unit-level TDD favors cohesive, loosely coupled responsibilities [3]. **Apply:** treat awkward setup, unclear failures and brittle coupling as design feedback; preserve readable behavior-focused tests, not incidental implementation choreography.
- **Synchronization is a design concern.** **Evidence:** Pryce links unreliable system tests to inadequate observation/synchronization, and cascading failures to inability to wait for inactivity and restore known state [3]. **Apply:** expose observable completion/failure, useful diagnostics and safe reset; synchronize on meaningful state rather than papering over races with sleeps. Ch. 27, “Distinguish Synchronizations and Assertions,” p. 326, is a further-reading pointer only [4].
