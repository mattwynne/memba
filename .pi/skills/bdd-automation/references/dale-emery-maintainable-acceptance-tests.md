# Dale H. Emery: Writing Maintainable Automated Acceptance Tests

Source: [Dale H. Emery, *Writing Maintainable Automated Acceptance Tests* (PDF)](https://dhemery.com/pdf/writing_maintainable_automated_acceptance_tests.pdf). Originally presented at Agile Development Practices 2009; the PDF says it has minor subsequent changes. These are paraphrased reading notes, not a reproduction of the paper. Page numbers below are the printed page numbers.

- **Automation is software development** (pp. 1–2). Maintenance is expected: tests must adapt to changing responsibilities and changing implementation. Incidental implementation details and duplication make changes expensive.
- **Acceptance concerns responsibility, not technology** (p. 2). Emery describes the essence of an acceptance test as the system responsibility it investigates, whether the system is a CLI, web app, or something else. This complements Ham Vocke's separate argument about acceptance purpose and test level; Emery does not claim every acceptance check must run through a browser.
- **Separate essential behaviour from incidental mechanics** (pp. 3–5). In his password example, the rule and outcomes matter; the command invocation, framework syntax and unrelated username do not. Put mechanical details in adapter/keyword support; express the responsibility in the readable test. Do not hide a mechanism that is itself the risk under test.
- **Name repeated concepts and meaningful values** (pp. 6–8). Repeated action/assertion pairs point to concepts such as accepting and rejecting a password. Name those concepts once in reusable support and name boundary values by why they matter (missing letters, minimum length, too long). Split an overstuffed test into focused tests that expose individual responsibility areas. Do not mechanically eliminate every repeated line: Emery explicitly asks whether further abstraction would actually improve clarity (p. 7, note 8).
- **Changes should be local when the contract remains the same** (pp. 9–10). His illustrative CLI-to-web rewrite changes low-level interaction keywords, not the responsibility-level tests. He warns that a real migration could involve more changes or even new tools; this is an example of a maintainable seam, not a promise of zero migration work.
- **Do not mistake a success message for the whole outcome** (p. 7, note 7). Emery notes that an account-creation check should also establish that the account was actually created, not only trust a reported status. Check the outcome that matters to the user.

Application boundary: These are source claims and examples. Any guidance about choosing a browser journey for a unique browser risk, prohibiting a click followed by forced direct navigation, or forbidding product-side JavaScript solely for tests is an additional decision in the skill, not attributed to Emery.
