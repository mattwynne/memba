# Gerard Meszaros: xUnit Test Patterns

Read when refactoring acceptance support, choosing fixture lifetimes or doubles, or diagnosing checks that are difficult to understand, order-dependent, or coupled to implementation details.

## Attribution and scope

**Gerard Meszaros**, *xUnit Test Patterns: Refactoring Test Code*, Addison-Wesley Professional, 2007, ISBN 9780131495050 ([publisher metadata](https://www.informit.com/store/xunit-test-patterns-refactoring-test-code-9780131495050)). These notes use selected public pattern descriptions, not a full-book reading. Meszaros catalogs practices and trade-offs; this is not a claim that he invented every technique.

The [author's site](http://xunitpatterns.com/) warns that its material differs from the copy-edited book; individual pages also warn of changes. Below, linked names and definitions are his terminology; **Application** explicitly marks our proposed BDD guidance, not his prescription for interchangeable domain/service/browser adapters.

## Reuse without hiding the example

- **[Test Utility Method](http://xunitpatterns.com/Test%20Utility%20Method.html)** encapsulates reusable test logic under a suitable name. Its **SUT Encapsulation Method / SUT API Encapsulation** variation wraps complicated application calls; helpers should emerge from actual tests, with explicit inputs/outputs. **Application:** build a small domain-language test API separating scenario intent from adapter mechanics. Preserve significant example values in the scenario; avoid speculative DSL infrastructure. Reuse adds another API to maintain, not automatically less complexity.
- **Terminology trap:** the site's **[test driver](http://xunitpatterns.com/test%20driver.html)** means a *person doing TDD*, not an adapter object. Our “driver” and “test DSL” are architectural vocabulary, not verified Meszaros pattern titles. Likewise, his **Behavior Verification** below means interaction verification, not BDD generally.

## Fixtures: share construction, not accidental state

- **[Inline Setup](http://xunitpatterns.com/Inline%20Setup.html)** keeps simple construction visible; **[Delegated Setup](http://xunitpatterns.com/Delegated%20Setup.html)** calls reusable creation methods while retaining relevant inputs; **[Implicit Setup](http://xunitpatterns.com/Implicit%20Setup.html)** uses framework-invoked setup. **Application:** keep business preconditions explicit and delegate incidental construction. Reserve common hooks for genuinely common prerequisites; a hook reusing setup code need not share fixture instances.
- **[Fresh Fixture](http://xunitpatterns.com/Fresh%20Fixture.html)** is private to one execution; **[Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)** reuses instances to reduce setup cost, risking collisions, obscurity and maintenance coupling. Meszaros suggests considering an **Immutable Shared Fixture** before mutable sharing. **Application:** recreate mutable scenario state for each adapter run; consider immutable reference data separately. Share builders rather than accounts, sessions or records that scenarios mutate. A persistent namespace alone is not a fresh fixture if subsequent runs reuse its contents.
- **[Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)** includes **Interacting Tests**, **Lonely Test** and **Test Run War**: dependencies or collisions across tests/runs undermine reliability. **Application:** verify scenarios alone, in changed order and concurrently where supported; isolate identifiers, sessions and external resources, and ensure cleanup after failure. Keep a coherent journey internally sequential, not dependent on another scenario's success.

## Doubles and verification: state what the evidence proves

- **[Test Double](http://xunitpatterns.com/Test%20Double.html)** replaces a depended-on component, not the functionality being tested. **[Test Stub](http://xunitpatterns.com/Test%20Stub.html)** supplies indirect inputs; **[Fake Object](http://xunitpatterns.com/Fake%20Object.html)** supplies a lightweight working implementation; **[Test Spy](http://xunitpatterns.com/Test%20Spy.html)** records indirect outputs for later assertions; **[Mock Object](http://xunitpatterns.com/Mock%20Object.html)** verifies expected interactions. **Application:** choose by purpose, not mocking-library branding. Fakes can accelerate rule examples, but cannot prove real provider compatibility. Preserve separate real-integration evidence; never replace the action under examination with a canned success.
- **[State Verification](http://xunitpatterns.com/State%20Verification.html)** compares resulting state; **[Behavior Verification](http://xunitpatterns.com/Behavior%20Verification.html)** checks indirect outputs/interactions. The latter can overspecify implementation. **Application:** prefer observable business outcomes when sufficient; assert interactions when those effects matter. Define each adapter's observation boundary explicitly: database state alone does not prove browser rendering, and a mail spy proves a request to send, not delivery. Do not impose one verification mechanism across incompatible risks.
- **[Custom Assertion](http://xunitpatterns.com/Custom%20Assertion.html)** receives comparison inputs without retrieving state; its **Verification Method** variation interacts with the SUT. **[Assertion Message](http://xunitpatterns.com/Assertion%20Message.html)** makes failures identifiable and diagnostic. **Application:** separate boundary-specific observation from reusable business comparison; report scenario, adapter, expected and actual outcome. Test nontrivial assertion helpers, including their failure paths.

## Readability and trustworthy failure

**[Obscure Test](http://xunitpatterns.com/Obscure%20Test.html)** can result from too much irrelevant detail or too little visible context (**Mystery Guest**). **[Conditional Test Logic](http://xunitpatterns.com/Conditional%20Test%20Logic.html)** complicates confidence that the intended check executes. **Application:** keep each example's cause and expected effect visible. Select adapters outside scenario logic; never branch around an assertion because a button or result is absent. Put necessary polling or collection comparison in small tested helpers with bounded failure, not success-shaped fallbacks. Extraction alone does not make faulty logic trustworthy.
